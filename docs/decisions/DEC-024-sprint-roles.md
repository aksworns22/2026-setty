# DEC-024 첫 개발 역할 구조

- 상태: **합의·실제 역할 배정 반영**
- 결정일: 2026-08-05, 후속 수정 2026-08-05
- 참여자: 캐리, 스마일, 밀란, 타스, 코코

## 문제

추상적인 Sprint·역할·작업 카드 체계가 팀에게 익숙하지 않아 각자 무엇을 구현해야 하는지 바로 이해하기 어려웠다.

## 검토한 구조

- 제품·문서·프론트·백엔드·통합 등 추상 결과 역할
- 프론트 환경·연동, 백엔드 환경·DB, 통합의 5개 환경 역할
- 사용자 흐름을 기준으로 예상 견적 2명, 배차 요청 3명 분담

## 결정

- 예상 견적 요청은 FE 1명과 BE 1명이 맡는다.
- 배차 요청은 FE 1명과 BE 2명이 맡는다.
- 각자는 자신의 GitHub Issue를 만들고 같은 흐름 동료와 지정 검토자가 범위를 먼저 확인한다.
- 별도 작업 카드 문서를 운영하지 않고 GitHub Issue를 실제 작업 단위로 사용한다.
- 정형화된 Sprint 운영은 당장 강제하지 않는다. 두 흐름이 개발 환경에서 작동하는 결과를 기준으로 진행한다.
- 공통 레포·실행 환경은 한 명이 먼저 설정하고 다섯 명 모두 새 clone에서 재현한 뒤 기능 작업으로 나뉜다.

## 역할

| 역할 | 담당 |
|---|---|
| 견적 FE | 캐리 |
| 견적 BE | 밀란 |
| 배차 FE | 스마일 |
| 배차 BE1 — 구매자 요청과 판매자 링크 | 타스 |
| 배차 BE2 — 판매자 입력과 운영자 조회 | 코코 |

초기 레포 설정 담당은 밀란, 검토자는 스마일이다. 변경 시 `docs/team/roles-and-ownership.md`와 실제 GitHub Issue를 함께 갱신한다.

## 이유와 우려

사용자 흐름별로 결과가 보여 팀원이 첫 행동을 이해하기 쉽다. 배차 요청은 범위가 커 BE를 둘로 나누지만, 공통 모델과 API 계약을 먼저 합의하지 않으면 충돌할 위험이 있다.

## 영향

- 관련 문서: `docs/team/roles-and-ownership.md`, `initial-development-plan.md`, `github-workflow.md`
- 관련 Issue: 공통 환경 1개, 견적 FE·BE 2개, 배차 FE·BE1·BE2 3개
- 개발 차단: 같은 흐름 담당자가 화면·API·DB 공통 계약을 승인하기 전 해당 기능 구현 보류
- 사용자 공개 차단: DEC-020·021과 운영 리허설 미완료
- 재검토: 두 흐름 통합 후 작업량 불균형 또는 충돌이 확인될 때

## 대체

이 결정은 같은 DEC의 이전 `프론트 환경·프론트 연동·백엔드 환경·백엔드 DB·통합` 구조와 별도 Sprint 1 카드 계획을 대체한다.
