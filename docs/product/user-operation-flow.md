# SETTY 사용자·운영 흐름

- 상태: **워크북 반영본·팀 대조 검토 필요**
- 기준일: 2026-08-05
- 핵심 원칙: 예상 견적 요청과 배차 요청은 자동으로 이어지는 한 요청이 아니라 별도의 사용자 행동과 기록이다.

## 1. 참여자와 정보 범위

| 참여자 | 입력·처리 정보 | 확인 가능한 정보 | 확인할 수 없는 정보 |
|---|---|---|---|
| 구매자 | 본인 이름·연락처, 거래 지역 또는 수령 상세주소, 물품 정보·사진 | 본인 요청 결과, 판매자 입력 완료 여부, 최종 금액과 진행 상태 | 판매자의 이름·연락처·상세주소, 운영 메모 |
| 판매자 | 본인 이름·연락처, 발송 상세주소, 발송 가능 시간 | 본인 입력 결과와 필요한 안내 | 구매자의 이름·연락처·상세주소, 운영 메모 |
| SETTY 운영자 | 요청 검토, 운송 판단, 가격·문자·배차·예외 기록 | 서비스 처리에 필요한 구매자·판매자 정보 | 업무와 무관한 추가 개인정보 |
| 운송자 | 실제 픽업·배송 수행 | 구매자·판매자 이름·연락처, 픽업·수령 상세주소, 픽업 시간 등 업무상 최소 정보 | SETTY 운영 메모와 실험 데이터 |

**[팀 확정]** 구매자와 판매자의 상세주소와 연락처를 서로의 화면에 직접 노출하지 않는다. 운영자와 운송자에게는 업무상 필요한 최소 정보만 제공한다.

## 2. 전체 진입 구조

```text
홈
├─ 예상 견적 요청
│  └─ 운영자의 예상 견적 문자
│     ├─ 아무 행동 없이 종료
│     └─ 문자 링크의 '견적 신청하기'로 새 배차 요청 시작
└─ 배차 요청하기

새 배차 요청
→ 구매자가 실제 거래 내용을 다시 입력
→ 판매자 입력 링크 발급·전달
→ 판매자가 픽업 정보 입력
→ 운영자 최종 검토·금액 문자 안내
→ 구매자 동의 또는 거절
→ 운영자 수동 착불 배차
→ 완료·실패·취소
```

예상 견적 요청은 `견적 안내 완료`에서 끝난다. 이후 링크를 눌러도 같은 요청의 다음 상태로 이어지지 않고 별도의 배차 요청이 생성된다. 기존 입력은 자동 복사하지 않는다.

## 3. 예상 견적 요청 흐름

### 입력

| 항목 | 필수 여부 | 비고 |
|---|---|---|
| 이름 | 필수 | 연락·요청 식별 목적 |
| 연락처 | 필수 | 운영자 문자 응답 목적 |
| 거래 지역 | 필수 | 상세주소가 아닌 대략 지역 |
| 물품 종류 | 필수 | 운영 판단 기초 정보 |
| 50만 원 초과 여부 | 필수 | 위험 안내·운영 판단 보조 |
| 물품 사진 | 선택 | 운영 판단 보조, 공개 전 저장 정책 검증 필요 |
| 개인정보 수집 동의 | **[공개 전 확정 필요]** | DEC-020 완료 전 실제 개인정보 접수 금지 |

### 정상 흐름

1. 사용자가 홈에서 `예상 견적 요청`을 선택한다.
2. 사용자가 필수 정보를 입력하고 제출한다.
3. 시스템은 형식을 검증해 요청을 `검토 대기`로 저장한다.
4. 사용자에게 운영자가 수동으로 확인한다는 접수 결과를 보여준다.
5. 운영자가 물품과 지역을 보고 운송 가능 여부와 예상 차량을 판단한다.
6. 운영자가 외부 채널에서 예상 가격을 직접 조회한다.
7. 운영자가 예상 금액·변동 가능성·다음 선택을 문자로 직접 안내한다.
8. 요청 상태는 `견적 안내 완료`가 된다.
9. 사용자는 종료하거나 문자 링크로 별도의 배차 요청을 시작한다.

### 정보 부족

1. 운영자가 판단에 필요한 추가 정보를 확인한다.
2. 운영자가 사용자에게 문자 등으로 직접 요청하고 상태를 `추가 정보 대기`로 바꾼다.
3. 사용자가 보완하면 시스템 또는 운영자가 `검토 대기`로 되돌린다.
4. **[팀 확인 필요]** MVP에서 보완 입력 전용 화면을 만들지, 문자 회신으로만 받을지 다음 기능 Sprint 전에 정한다.

### 운송 불가

1. 운영자가 현재 가능한 운송 수단으로 어렵다고 판단한다.
2. 운영자가 내부 사유를 기록하고 사용자에게 필요한 수준의 사유를 직접 안내한다.
3. 상태를 `운송 불가`로 종료한다.

### 사용자 취소

사용자가 취소 의사를 밝히면 운영자가 확인해 `사용자 취소`로 종료한다. **[팀 확인 필요]** 사용자가 직접 누르는 취소 기능은 후속 범위에서 결정한다.

### 운영시간 밖·지연

- 시스템은 24시간 접수한다.
- 20:00~10:00 접수에는 다음 운영 시작 후 처리한다는 안내를 보여준다.
- 운영시간 내 5분은 내부 목표이며 즉시 응답 보장이 아니다.
- 목표를 넘길 경우 캐리가 지연 문구를 준비하고 운영 담당자가 직접 안내한다.

## 4. 배차 요청 흐름

### 시작 방법

- 예상 견적 문자 링크의 `견적 신청하기`를 선택한다.
- 예상 견적 없이 홈에서 `배차 요청하기`를 선택한다.

두 방법 모두 새 배차 요청을 생성한다. 예상 견적 정보 재사용 없이 구매자가 실제 거래 내용을 다시 입력한다. 여기서 배차 요청은 SETTY 운영자에게 배송 조율을 요청한다는 뜻이며 운송사에 자동 접수한다는 뜻이 아니다.

### 구매자 입력

- 이름
- 연락처
- 수령 상세주소
- 물품 종류
- 물품 사진(필수)
- 50만 원 초과 여부
- 개인정보 수집 동의 **[공개 전 확정 필요]**

시스템은 판매자 입력 세션과 연결된 링크를 발급하고 구매자가 외부 메신저로 판매자에게 직접 전달한다.

### 판매자 입력

1. 판매자가 전용 링크에 접속한다.
2. 이름, 연락처, 발송 상세주소, 발송 가능 시간을 입력한다.
3. 시스템은 구매자에게 판매자 정보의 내용이 아니라 `입력 완료 여부`만 보여준다.
4. 시스템은 배차 요청을 `최종 검토 대기`로 변경한다.

### 최종 금액과 배차

1. 운영자가 양쪽 입력을 확인한다.
2. 운영자가 운송 가능 여부와 차량을 다시 판단한다.
3. 운영자가 실제 주소와 시간으로 최종 금액을 조회한다.
4. 운영자가 최종 금액과 조건을 구매자에게 문자로 직접 안내한다.
5. 구매자가 동의 또는 거절한다.
6. 동의하면 운영자가 외부 운송 채널에서 착불로 수동 배차한다.
7. 운영자가 배차·운송·완료 상태를 기록하고 양쪽에 필요한 문자를 직접 보낸다.

### 실패·취소·지연

- 판매자 미입력: 운영자가 구매자에게 진행이 멈춘 이유와 다음 행동을 안내한다.
- 최종 운송 불가: 운영자가 양쪽에 필요한 사유를 안내하고 종료한다.
- 최종 금액 거절: `최종 금액 거절`로 종료한다.
- 기사 미배정: `배차 실패`로 기록하고 대체 수단 또는 지연 여부를 직접 협의한다.
- 배차 후 취소: 운영자가 외부 채널의 실제 조건을 확인한 뒤 처리한다.
- 배송 중 문제: 운영자가 운송자·구매자·판매자와 직접 소통하고 결과를 기록한다.

## 5. 상태와 변경 주체

내부 상태와 사용자 표시 문구를 분리한다.

### 예상 견적 상태

| 내부 상태 | 사용자 표시 | 변경 주체 | 종료 |
|---|---|---|---|
| `검토 대기` | 요청을 확인하고 있어요 | 제출 시 시스템 | 아니요 |
| `추가 정보 대기` | 추가 정보가 필요해요 | 운영자 | 아니요 |
| `견적 안내 완료` | 예상 견적을 안내했어요 | 운영자 | 예 |
| `운송 불가` | 현재 조건으로 진행하기 어려워요 | 운영자 | 예 |
| `사용자 취소` | 요청이 취소됐어요 | 사용자 의사 확인 후 사용자 또는 운영자 | 예 |

### 배차 요청 상태

| 내부 상태 | 사용자 표시 | 변경 주체 | 종료 |
|---|---|---|---|
| `판매자 입력 대기` | 판매자 정보를 기다리고 있어요 | 배차 요청 시 시스템 | 아니요 |
| `최종 검토 대기` | 배송 조건을 확인하고 있어요 | 판매자 입력 완료 시 시스템 | 아니요 |
| `최종 금액 확인 대기` | 최종 금액 확인이 필요해요 | 운영자 | 아니요 |
| `배차 대기` | 배차를 준비하고 있어요 | 구매자 동의 | 아니요 |
| `배차 완료` | 기사가 배정됐어요 | 운영자 | 아니요 |
| `운송 중` | 배송이 진행 중이에요 | 운영자 | 아니요 |
| `배송 완료` | 배송이 완료됐어요 | 운영자 | 예 |
| `최종 금액 거절` | 최종 금액을 거절해 종료됐어요 | 구매자 | 예 |
| `운송 불가` | 현재 조건으로 진행하기 어려워요 | 운영자 | 예 |
| `사용자 취소` | 요청이 취소됐어요 | 배차 전 사용자 의사 확인 후 처리 | 예 |
| `배차 실패` | 배차가 어려워 운영자가 안내할 예정이에요 | 운영자 | 예 |

종료된 예상 견적을 배차 요청 상태로 바꾸지 않는다. 문자 링크로 생성된 배차 요청과 원본 예상 견적은 서로 다른 상태를 가진다.

## 6. 시스템과 사람의 책임

| 단계 | 시스템 | 운영자 |
|---|---|---|
| 접수 | 입력 형식 검증, 저장, 상태 표시 | 신규 요청 확인 |
| 운송 판단 | 판단 정보 제공·결과 저장 | 가능 여부와 차량 판단 |
| 가격 | 운영자가 입력한 값·조회 시각 저장 | 외부 채널에서 직접 조회 |
| 문자 | 템플릿·발송 기록 지원 | 실제 문자 발송 |
| 판매자 연결 | 링크 발급·접근 제한·완료 상태 | 필요 시 입력 독려 |
| 최종 동의 | 동의·거절 결과 저장 | 최종 금액 직접 안내 |
| 배차 | 운영 상태 기록 | 외부 채널에서 수동 배차 |
| 예외 | 상태·사유·결과 기록 | 당사자와 직접 해결 |
